# Sherlock

Sherlock is a local desktop workspace for reviewing potential repository secrets and preparing redacted Git branches. It uses Rust and egui, with a thin interface over scanner and Git operations.

## Architecture

The workspace separates the finding model, scanner adapters, review storage, Git operations, history rewriting, and desktop interface. See [Architecture](docs/architecture.md) for the crate responsibilities and their interfaces.

## Requirements

- Rust and Cargo
- Git
- [Gitleaks](https://github.com/gitleaks/gitleaks) and/or [TruffleHog](https://github.com/trufflesecurity/trufflehog) on `PATH`

Run `cargo run --release`.

## Workflow

1. Choose a local repository and scan it with either scanner or both. Matching reports with the same commit, path, line, and detected value are grouped; ambiguous reports remain separate. Findings and secret values remain in memory; values are masked in the interface. Exact detected values are grouped for review; you can also link or unlink distinct detected values. Classifications remain specific to each finding and default to potential secrets; you can mark false positives or accepted risks. Review decisions are stored locally across scans and restarts using a hash of the repository path, location, and detected value; raw reports and values are not written to the review file. Reports missing identifying fields cannot be marked. Related-value links use repository-scoped keyed identifiers and a key stored in the system credential store; raw values are not stored in the links file. Keep the credential-store key with your backups: losing it makes saved links unavailable. Sherlock registers generated mirrors to their original workspace; this requires the original repository path to remain available and unmoved. Saved links can also be inspected and removed when a value is not reported in the current scan; its value is not recoverable from the saved link.
2. Fetch remotes when needed, select a finding, and find local and remote-tracking refs containing any known commit with the same exact detected value. The resolution page can list scanner-reported occurrence commits and the refs containing them; it does not infer moves or disappearance. Fetch can change local remote-tracking refs and prune stale ones.
3. Select refs and create redacted branches in a **new mirror**. Each selected ref becomes `refs/heads/sherlock/redacted-N`; the activity panel lists the mapping. The exact detected value is replaced throughout each selected branch's history, not just at the reported location. The source repository is not rewritten and nothing is pushed.
4. After each rewrite Sherlock checks the exact detected value in reachable file blobs at the recorded output tips and reruns the selected scanner on each output branch. You can rerun either check from the resolution page. These checks have different coverage and do not prove that history is free of secrets. Scanner findings can be brought back into discovery in the new mirror for another iteration. If the exact-value check finds a match, you can locate it by commit and path and review those occurrences, including matches scanners did not report. Locating matches can be slow on large histories; binary blobs are detected but not rewritten. The mirror’s original refs remain sensitive. After reviewing both check results, a developer can record completion for the recorded output tips. The completion record is historical and does not establish that other linked values or current refs are clean. Independently inspect the results before sharing or pushing. The mirror also retains original refs and objects, including the secret. Treat the entire mirror as sensitive. Rewriting history does not revoke exposed credentials: rotate them separately.

## Current limitations

This is an early local workflow, not an automated remediation guarantee. Scanners have their own coverage and may miss secrets. The built-in `sherlock-rewrite` crate handles literal replacements in text blobs, including multiline values. It is purpose-built for this workflow and does not implement all of git-filter-repo’s features. One exact value is processed per mirror; linked variants and multiple distinct secrets require additional work. Findings without a commit cannot identify affected branches. Git LFS, submodules, binary files (blobs containing a NUL byte), commit/tag messages, encoded variants, and provider-side pull requests or caches are not remediated. The exact-value check covers reachable file blobs, including binary blobs, but excludes commit/tag messages, LFS payloads, submodule repositories, and unselected refs; it rejects shallow repositories and repositories with Git grafts. Scanner results depend on the scanner’s own history and detection coverage. Rewriting changes commit IDs; signatures and embedded merge tags are removed from rewritten commits because they are no longer valid. Review repository policy and coordinate any eventual force push. If a rewrite fails, its destination may be left behind and must be inspected or removed manually. TruffleHog credential verification is disabled. Scan reports are temporarily written to a private temporary file by Gitleaks and removed after the scan.
