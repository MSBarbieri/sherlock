# Git history redaction: semantics and verification

Research for [What Git history cases must a Rust rewrite engine preserve?](https://github.com/MSBarbieri/sherlock/issues/5). This is a decision input, not a specification or a claim that the prototype implements these cases. Sources consulted 2026-11-05.

## Graph and objects

A commit names a tree and zero or more parents; multiple parents represent a merge. Changing a blob changes its tree and consequently the ID of each affected commit and descendants whose parent IDs change. Preserve the ordered parent list, roots, merges, and sharing, and maintain an old-to-new mapping across all selected roots; don't infer history from filenames alone. Preserve tree entry names and modes (including executable bits and symbolic links), as well as unrelated bytes. Git objects are content-addressed; even a metadata change changes the commit ID. [Git objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [git-commit-tree](https://git-scm.com/docs/git-commit-tree).

Git blobs are byte sequences, not intrinsically text. A text-only matcher cannot establish that a secret is absent from binary data, alternate encodings, compressed content, filenames, commit/tag messages, or other metadata. Define supported replacement semantics and report unexamined material rather than treating a successful pass as complete. [git-cat-file](https://git-scm.com/docs/git-cat-file), [git-filter-branch security checklist](https://git-scm.com/docs/git-filter-branch#_checklist_for_shrinking_a_repository).

Author, committer, timestamps, message, encoding and additional commit headers can matter. A signature authenticates particular object content, so modifying that content invalidates its signature; preserving the old signature as though valid is incorrect. Git's export tool explicitly requires a policy for signed tags and signed commits. Decide whether to strip signatures with an explicit report, re-sign, or reject; do not silently claim historical signatures survive. [Git signature format](https://git-scm.com/docs/signature-format), [git-fast-export](https://git-scm.com/docs/git-fast-export), [git-commit-tree](https://git-scm.com/docs/git-commit-tree).

## Scope and references

A branch is a ref, not the commit itself. The set of refs to inspect and rewrite must be explicit and snapshotted: local branches, fetched remote-tracking refs, tags and other namespaces may point into the same history. A remote-tracking ref describes the last fetched state; it is not proof of all refs on a server, inaccessible refs, forks or other clones. `clone --mirror` maps all refs advertised by the source, but that remains bounded by what the server advertises and permissions allow. Refresh and enumerate the intended scope and report it precisely. [git-clone](https://git-scm.com/docs/git-clone), [git-fetch](https://git-scm.com/docs/git-fetch), [git-ls-remote](https://git-scm.com/docs/git-ls-remote).

Annotated tags are objects with their own metadata and possibly signatures; lightweight tags are refs. Tags can point to objects other than commits. Retargeting a tag can therefore require rewriting its object and invalidates a signature over changed contents. Decide which refs and tag types to support and how to expose untouched references. [git-tag](https://git-scm.com/docs/git-tag), [git-fast-export](https://git-scm.com/docs/git-fast-export).

Stage rewritten objects and verify them before creating output refs. For concurrent changes, use expected old values and a ref transaction; `git update-ref --stdin` supports prepare/commit transactions and old-value checks. This guards against updating a ref that moved during the operation; it does not make objects or other clones disappear. Record old/new ref and commit mappings and failures without recording secret values. [git-update-ref](https://git-scm.com/docs/git-update-ref).

Old objects can remain reachable via other refs, reflogs, backups, alternate object stores or other copies; unreachable objects can persist until garbage collection. A new branch or successful rewrite does not remove the original from a remote or collaborators' clones. Treat the isolated workspace as sensitive, explain the exact scope of verification, and provide separate guidance for credential revocation/rotation and distribution cleanup. [git-filter-branch checklist](https://git-scm.com/docs/git-filter-branch#_checklist_for_shrinking_a_repository), [git-reflog](https://git-scm.com/docs/git-reflog), [git-gc](https://git-scm.com/docs/git-gc).

## Repository boundaries and formats

- **Shallow and partial clones:** shallow history deliberately omits ancestors; partial clone filters omit objects and may fetch them later from a promisor remote. Detect these conditions before claiming complete coverage, obtain the needed data or explicitly block/mark verification incomplete. A network-dependent fetch can fail. [git-clone](https://git-scm.com/docs/git-clone), [partial clone design](https://git-scm.com/docs/partial-clone), [shallow repository](https://git-scm.com/docs/shallow).
- **Submodules:** a superproject tree contains a gitlink to a commit in a separate repository; its contents are not ordinary blobs in the superproject. Rewriting a superproject alone cannot clean the submodule's history. Define recursive discovery, access and independent reporting or explicitly exclude it. [gitsubmodules](https://git-scm.com/docs/gitsubmodules).
- **Git LFS:** Git stores a pointer to externally stored content; scanning/replacing the pointer alone does not inspect or remove the LFS payload. LFS payload cleanup and remote retention need their own scope and authorization. [Git LFS specification](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md).
- **Object format:** Git supports SHA-1 and SHA-256 repository formats, whose object IDs differ in length and whose object representations include format-specific references. Avoid assuming a fixed 40-character ID; detect the repository format and either support it end to end or fail clearly. [git-init](https://git-scm.com/docs/git-init), [hash function transition](https://git-scm.com/docs/hash-function-transition).
- **Other repository layouts:** linked worktrees, bare repositories, alternates and replace refs affect where refs/objects live or which object is read. Resolve via Git's repository interfaces and explicitly decide whether replacements and alternates are allowed; do not assume a conventional `.git` directory is self-contained. [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout), [git-worktree](https://git-scm.com/docs/git-worktree), [git-replace](https://git-scm.com/docs/git-replace).

## Verification and unresolved choices

A defensible result distinguishes object integrity, intended transformation, and secret detection. `git fsck` verifies object connectivity and validity; it is not a secret scanner and cannot prove content clean. Independently enumerate every object reachable from the *declared output refs*, compare rewritten graph topology and unaffected entries/metadata against the original, check intended replacement coverage, and run configured scanners on the output history. Report scanner errors, skipped data and incomplete input separately from a clean result. Preserve evidence such as scoped ref IDs, tool versions, rules and checks, without persisting the secret. [git-fsck](https://git-scm.com/docs/git-fsck), [git-rev-list](https://git-scm.com/docs/git-rev-list), [git-diff-tree](https://git-scm.com/docs/git-diff-tree).

Decisions still needed: permitted input/ref scope; whether secrets in messages, paths or binary data are in scope; handling tags, signatures, LFS and submodules; clone completeness and SHA-256 support; required independent checks and the definition of a clean result; and user-visible treatment of originals, other clones, remote hosting and rotation. A scanner's negative result is evidence from its rules and coverage, not proof that all secrets are gone.
